# Архитектурное ревью: цепочка оценка тикета → кодер → ревьюер → UI-тестировщик

Ревью на уровне архитектуры системы в целом, а не отдельных решений
по ходу обсуждения. Разбито по критичности: что заблокирует запуск в
продакшн, что аукнется через месяц эксплуатации, что можно
сознательно отложить.

---

## Критично — до первого реального запуска

### 1. Хук — единая точка отказа без своей защиты [РЕШЕНО]

**Решение**: хук держим тонким — только маршрутизация и запись
состояния, сложная логика (механическая проверка тестов и т.п.)
вынесена в отдельные, независимо тестируемые скрипты, которые хук
вызывает. Весь диспетчер обёрнут в try/catch на верхнем уровне —
любое необработанное исключение пишет в состояние отметку "хук упал"
и уходит по тому же пути эскалации, что и исчерпанный лимит попыток,
без отдельного механизма. Плюс таймаут на каждый шаг — зависание тоже
считается сбоем, а не бесконечным ожиданием.

### 2. Механическая проверка тестов манипулирует рабочим деревом git [РЕШЕНО]

**Решение**: работа всегда идёт в выделенной ветке по номеру тикета
(например `KAZ-112`), на которой параллельно больше никто не
работает. Это снимает основной риск — нечего случайно съесть чужими
незакоммиченными изменениями. Отдельный git worktree — опциональная
доп. страховка, не жёсткое требование; механическую проверку тестов
можно делать через `stash` прямо в этой ветке, раз она гарантированно
эксклюзивна для задачи.

### 3. Извлечённые критерии — единая точка правды без проверки [РЕШЕНО]

**Рассмотренные варианты**:
- A. Сырой текст тикета едет дальше по цепочке как справочный
  материал, не только извлечённые критерии — дёшево, без лишнего
  вызова модели.
- B. Агент оценки сам перечитывает свои же критерии — слабый вариант,
  та же слепая зона, что и при первом извлечении.
- C. Ревьюер на первой итерации сверяет критерии с оригиналом тикета,
  не только diff с критериями — использует уже оплаченный вызов
  модели, ловит неверную экстракцию в том же месте, где и так идёт
  рассуждение.

**Решение**: A + C вместе. Текст тикета едет как дешёвый пассивный
контекст, а ревьюер на первой итерации явно сверяет критерии с
оригиналом, а не только diff с критериями — ловит сценарий, где
триаж понял тикет неправильно, без отдельного агента.

## Высокий приоритет — аукнется в эксплуатации

### 4. Бюджет по токенам не ограничен, только по числу попыток [РЕШЕНО]

Три попытки — это защита от бесконечного цикла, но не от дорогого
цикла. Если diff большой, а UI-тестировщик гоняет визуальную модель
по скриншотам на каждом шаге, три попытки могут стоить неожиданно
много на одном тикете.

**Решение**: бюджет по токенам добавляется рядом со счётчиком
попыток, в тот же `.work/<id-тикета>/state/counter.json` — хук
суммирует токены каждого вызова (кодер, проверка тестов, ревьюер,
UI-тестировщик) и останавливает цепочку тем же путём эскалации, что
и лимит попыток, если совокупный расход превышает потолок — даже
если формально попыток ещё меньше трёх. Число итераций и бюджет
токенов — два независимых предохранителя, оба должны быть пройдены,
не один вместо другого.

### 5. Тавтологичные тесты закрыты только наполовину [РЕШЕНО]

Механическая проверка "падает без кода, проходит с кодом" ловит
тесты, которые вообще ничего не проверяют, но не ловит тесты, которые
привязаны к деталям реализации, а не к наблюдаемому поведению из
критериев приёмки. Под давлением лимита в три попытки у кодера есть
стимул написать тест, который технически проходит эту механическую
проверку, но не отражает то, что просил тикет.

**Рассмотренные варианты**:
- A. Промпт ревьюера явно требует смысловой проверки — тест должен
  отражать исход из критериев приёмки, а не деталь реализации.
  Дёшево, качество зависит от суждения модели в моменте.
- B. Mutation testing — точечные осмысленные поломки реализации,
  проверка, что тесты их ловят. Надёжнее, но тяжело строить
  правильно — оверкилл для старта.
- C. Трассируемость критерий → тест — каждый критерий приёмки имеет
  явно привязанный тест (id критерия в названии/докстринге). Не
  ловит тавтологичность саму по себе, но ловит пропущенное покрытие.

**Решение**: A + C вместе, в том же вызове ревьюера, что уже
происходит — не отдельный агент. Mutation testing (B) — возможный
апгрейд в будущем, если A+C на практике окажется недостаточно, не
строится сейчас.

### 6. Нет истории git для самих попыток [РЕШЕНО]

Не описано, что происходит с git-историей между попытками — каждая
правка кодера это новый коммит, амend прошлого, или отдельная ветка?

**Решение**: закрывается логикой чекпоинтов из пункта 7. Каждый
состоявшийся чекпоинт (кодер прошёл механическую проверку тестов,
ревью прошло) — отдельный коммит, не amend поверх предыдущего: иначе
нечего будет адресовать при резюмировании после остановки на лимите.
Полная эволюция понятна человеку через `attempt-N-session.md`, а не
через чтение git log — коммиты нужны для резюмирования, а не как
основной источник для разбора попыток.

### 7. Что происходит с кодом при остановке на лимите [РЕШЕНО]

Если лимит попыток исчерпан, код в рабочей ветке остаётся в
незавершённом, возможно нерабочем состоянии.

**Решение**: откатывается не вся ветка, а только незавершённый шаг, на
котором сработал лимит. Каждый успешно пройденный и провалидированный
шаг фиксирует чекпоинт (кодер прошёл механическую проверку тестов,
ревью прошло, тесты прошли) — ветка никогда не откатывается дальше
последнего состоявшегося чекпоинта. Если лимит сработал внутри
следующего шага, не дойдя до его завершения (например, во время
ревью, ещё до вердикта), этот незавершённый шаг просто отбрасывается,
а не забирает с собой уже провалидированную работу кодера.

При повторном запуске этого тикета работа продолжается со следующего
шага после последнего чекпоинта, а не с оценки тикета заново — чекпоинт
хранится в `.work/<id-тикета>/state/counter.json` вместе со счётчиком
попыток. Полная эволюция всех попыток (что менялось, что говорил
ревьюер, что показал тестировщик) остаётся в `attempt-N-session.md` —
человек разбирается по логам, а не по мусору в ветке. Само уведомление
"остановлено" указывает на логи конкретных попыток для разбора.

## Средний приоритет — стоит держать в уме, не блокер запуска

### 8. Конкурентный запуск одного и того же тикета [ИСКЛЮЧЕНО]

Если один и тот же тикет случайно попадёт в обработку дважды
параллельно (повторный вебхук, ручной перезапуск поверх ещё идущего),
запись в `.work/<id-тикета>/state/counter.json` может гонка условий
испортить.

**Решение**: исключено на уровне процесса — параллельный запуск одного
и того же тикета не происходит по дизайну, лок-файл и проверка "уже
выполняется" не нужны.

### 9. Версия промптов агентов не привязана к логам попыток [ИСКЛЮЧЕНО]

Промпты агентов будут меняться со временем. Если через полгода
понадобится разобраться, почему одна задача вела себя иначе другой,
может показаться, что `attempt-N-session.md` не скажет, какой версией
промпта ревьюера или кодера она была выполнена.

**Решение**: избыточно — `attempt-N-session.md` уже хранит сами
промпты, использованные в этой попытке, а не ссылку на версию. Раз
конкретный текст промпта зафиксирован буквально под номером итерации,
отдельный хэш или тег версии конфигурации ничего не добавляет.

### 10. Ревьюер совмещает две разных роли [НЕ ТРЕБУЕТСЯ СЕЙЧАС]

Он одновременно судит про качество кода (архитектура, тесты) и про
соответствие требованиям (критерии приёмки).

**Почему в принципе могло бы понадобиться разделение**: разная природа
знаний (инженерная экспертиза vs предметная/регуляторная), раздувание
промпта при росте правил комплаенса, разный темп изменения правил.

**Почему не делаем сейчас**: разделение — это ещё один субагент с
чистым контекстом и ещё одна точка, где может потеряться связь между
нарушением и самим diff — реальная цена без реального сигнала, что
она нужна. Возвращаемся к этому, только если на практике ревьюер
начнёт путать два типа проверки, а не заранее.

---

## Что сделано хорошо (не менять без причины)

- Разделение прав по ролям на уровне инфраструктуры, а не промпта —
  ревьюер и тестировщик физически не могут писать код.
- Минимальный доступ к тикет-системе — только один агент, остальные
  работают с уже извлечённым текстом.
- `.work/` как общий канал между субагентами поверх явной передачи
  через промпт — правильный баланс: детерминированный минимум в
  промпте, богатый контекст доступен по требованию через файлы.
- Механическая, а не оценочная проверка вменяемости тестов — там, где
  можно заменить суждение агента детерминированной проверкой, это
  сделано, и это снижает и стоимость, и непредсказуемость.

## Ревью #2 — после введения чекпоинтов и резюмирования

Логика "хранить последний чекпоинт, продолжать оттуда" сама по себе
хорошая, но она вводит новый класс вопросов, которых не было при
простом откате к baseline. Разбираю их отдельно.

### 11. Токен-бюджет не может прерывать выполнение на середине шага [РЕШЕНО]

Сценарий "лимит сработал во время ревью, до вердикта" на практике не
может быть буквальным прерыванием посреди работы модели — такой
возможности прервать уже идущий вызов на полпути обычно просто нет.

**Решение**: проверка бюджета — pre-flight, перед стартом шага, с
запасом QoS. Хук перед тем, как заспаунить следующего агента, смотрит
на остаток бюджета; если остаток меньше 5% от лимита — шаг не
стартует вообще, даже если формально что-то ещё осталось, тормозим
заранее, не впритык к нулю. Чекпоинтом остаётся то, что было до этого
шага. Внешне это выглядит как "остановились перед ревью", а не
"внутри ревью" — та же итоговая точка, но механизм другой.

### 12. Не определено, что запускает резюмирование [РЕШЕНО]

Есть данные (чекпоинт в `counter.json`), но нет описания, что именно
инициирует продолжение работы с этого чекпоинта.

**Решение**: тот же принцип, что и в петле "нужны уточнения" —
резюмирование происходит, когда тикет в следующий раз попадает в
очередь, тем же триггером, что запускает цепочку впервые, а не
отдельным механизмом. Основная сессия при получении задачи первым
делом проверяет `.work/<id-тикета>/state/` на существующий чекпоинт.

### 13. Тикет мог измениться за время между остановкой и резюмированием [РЕШЕНО]

Если чекпоинт "кодер прошёл" зафиксирован, а пока задача стояла,
кто-то отредактировал тикет — резюмирование с этого чекпоинта погонит
ревью против уже устаревших критериев незамеченно.

**Решение**: при резюмировании сверяется хэш содержимого тикета (или
дата апдейта) с моментом, когда были извлечены критерии. Если тикет
менялся — чекпоинт отбрасывается целиком, работа начинается заново с
оценки тикета, а не продолжается вслепую со старыми критериями.

### 14. Засчитывается ли попытка, если шаг не стартовал из-за бюджета [РЕШЕНО]

Если следующий агент не был запущен вообще (см. пункт 11), непонятно,
тратит ли это одну из трёх попыток, или это отдельная причина
остановки.

**Решение**: pre-flight-отказ по бюджету не тратит попытку из трёх —
это независимый предохранитель. `counter.json` хранит попытки и
бюджет как два отдельных поля, не один счётчик.

### 15. Дрейф окружения при долгой паузе перед резюмированием [РЕШЕНО]

Если ветка `KAZ-112` простояла с чекпоинтом долго, а основная ветка
ушла вперёд — резюмирование с чекпоинта может упереться в конфликт
при последующем мерже.

**Решение**: при резюмировании проверяется, не ушла ли main вперёд
относительно точки создания ветки тикета. Если да — чекпоинт
отбрасывается целиком, работа начинается заново от актуальной main,
без попытки автоматически разрешить возможный конфликт.

### 16. Нагрузка на ревьюера продолжает расти [ОТЛОЖЕНО]

Не переоткрываю решение "не разделять роли сейчас" (раздел 10) — но
стоит явно зафиксировать: за последние два раунда ревью ревьюер
получил ещё два новых типа проверки (сверка критериев с оригиналом
тикета, трассируемость критерий → тест) поверх исходных code quality
+ соответствие критериям + валидация сценария UI. Сигнал для будущего
пересмотра пункта 10 — не "разрослись правила комплаенса", а
"разрослось число разных типов проверки в одном промпте" вообще.

**Решение**: оставляем ревьюера как есть. Возвращаемся к разделению
только если на практике реально возникнут проблемы, не по ощущению
роста числа проверок.

**Архивирование `.work/<id-тикета>/` после закрытия тикета [ВЫНЕСЕНО]**

Разбирается отдельным процессом по мере необходимости, не в рамках
этой спецификации.

## Ревью #3 — согласованность между уже принятыми решениями

Это не новые риски с нуля, а стыки между решениями, принятыми в
разных раундах, которые начали противоречить друг другу или просто
не были состыкованы. Ничего пока не решено — только зафиксировано.

### 17. Тратит ли попытку сработавшая механическая проверка тестов [РЕШЕНО]

**Решение**: тратит. Код уже написан и не годится — это реальная
работа, которую нужно переделать, в отличие от pre-flight отказа по
бюджету, где работа даже не начиналась. `counter.json`: срабатывание
проверки инкрементирует счётчик попыток.

### 18. Создаётся ли чекпоинт при "неубедительной" проверке тестов [РЕШЕНО]

**Решение**: чекпоинт создаётся всё равно, иначе резюмирование после
случайного лимита теряет работу кодера. Чекпоинт помечается флагом
"unverified" — и резюмирование, и ревьюер видят эту пометку и знают,
что механическая проверка не была пройдена чисто, а не считают её
полноценным пройденным шагом.

### 19. "Первая итерация" для одноразовых проверок ревьюера [РЕШЕНО]

**Решение**: одноразовые проверки (сверка критериев с тикетом,
валидация сценария UI) привязаны не к номеру попытки, а к генерации
критериев. Агент оценки тикета присваивает критериям id/timestamp при
извлечении. Резюмирование в рамках той же генерации критериев не
повторяет эти проверки. Полный рестарт (новая генерация критериев
после смены тикета) — повторяет их заново, это и есть новая "первая
итерация" по факту.

### 20. Текст спецификации разошёлся с диаграммой [РЕШЕНО]

**Решение**: раздел 5 документа обновлён — хук после ревьюера явно
создаёт чекпоинт "review-passed" при прохождении, синхронно с тем,
что уже показывала диаграмма.

### 21. Отбрасывание чекпоинта при рестарте противоречит принципу сохранения истории [РЕШЕНО]

**Решение**: не удаление, а архивирование. При полном рестарте (смена
тикета или дрейф main) содержимое `.work/<id-тикета>/state/` и
`.work/<id-тикета>/screenshots/` переносится целиком, с зеркальной
структурой, в `.work/<id-тикета>/stale-<timestamp>/` (уточнено в
пункте 24 — архив на уровне корня тикета, не внутри `state/`), а не
стирается — принцип "человек видит полную историю" сохраняется даже
через рестарт. Новый цикл начинает чистые файлы состояния с нуля.

### 22. Нет верхнего предела на число рестартов "с нуля" [РЕШЕНО]

**Решение**: добавлен отдельный внешний предохранитель — не более 2
полных рестартов на тикет (то есть максимум 3 цикла по 3 попытки
каждый). Считается в файле верхнего уровня, который не архивируется
вместе с `state/` при рестарте (иначе сам счётчик рестартов
обнулялся бы вместе с состоянием, которое должен ограничивать).
Исчерпание — остановка тем же путём, что и обычный лимит попыток,
без дальнейших автоматических рестартов.

### 23. Не сохраняется снэпшот тикета для сравнения при резюмировании [РЕШЕНО]

**Решение**: агент оценки тикета пишет
`.work/<id-тикета>/state/ticket-snapshot.md` (сырой текст + хэш +
дата) в момент извлечения критериев — это и есть точка сравнения для
проверки из пункта 13.

## Ревью #4 — дыры в решениях раунда #3

Тот же принцип: не новые риски с нуля, а места, где только что
принятые решения (17–23) сами создали нестыковки или оставили
недосказанность. Ничего не решено — зафиксировано для решения.

### 24. Где именно живёт счётчик рестартов, и куда архивируется screenshots/ [РЕШЕНО]

**Решение**: архив — на уровне корня тикета, не внутри `state/`.
`.work/<id-тикета>/stale-<timestamp>/` зеркалит исходную структуру
целиком — внутри свои `state/` и `screenshots/`, перенесённые как
есть, а не смешанные в одну ветку. Счётчик рестартов —
`.work/<id-тикета>/restarts.json`, тоже на уровне корня, соседний с
`state/` и `screenshots/`, не архивируется, потому что обязан
пережить каждый рестарт, который сам же ограничивает.

### 25. Резюмирование в "unverified" чекпоинт [РЕШЕНО]

**Решение**: при резюмировании механическая проверка повторяется один
раз, не больше. Раз ветка на этот момент точно эксклюзивна,
исходная причина конфликта, скорее всего, уже неактуальна — дешёво
попробовать снова и получить чистый результат. Если повторная попытка
опять не применилась чисто — дальше идём с тем же флагом "unverified"
к ревьюеру, как и раньше, не зацикливаемся на повторных попытках
самой проверки.

### 26. Два идентификатора, риск разойтись [РЕШЕНО]

**Решение**: один источник правды. Хэш из `ticket-snapshot.md` — он
же и есть id генерации критериев, отдельного независимого id не
существует. Генерация критериев по определению привязана к
конкретной версии тикета, так что не нужно поддерживать два числа,
которые описывают одно и то же событие.

### 27. Тратит ли попытку "unverified"-чекпоинт [РЕШЕНО]

**Решение**: сам по себе — нет. Попытка тратится только в момент
однозначного исхода: тавтологичный тест (провал механической
проверки, пункт 17) или fail от ревьюера (обычная логика). Если
ревьюер, получив diff с флагом "unverified", всё равно проходит
проверку и говорит pass — работа кодера засчитывается, попытка не
потрачена, несмотря на то что механическая проверка была
неубедительной. Это держит счётчик попыток однородным: он реагирует
на однозначные провалы, а не на промежуточные состояния с
неопределённым исходом.

## Ревью #5 — найдено при переводе спецификации на английский

### 28. Fail от несоответствия критериев уходил кодеру вместо оценки тикета [РЕШЕНО]

Ревьюер теперь на первой итерации сверяет извлечённые критерии с
оригиналом тикета (решение по пункту 3, A+C). Но вердикт ревьюера
оставался бинарным pass/fail без указания причины, и любой fail шёл
по одному и тому же пути — в счётчик неудач, оттуда на доработку
кодеру. Если именно эта сверка проваливается — проблема не в коде, а
в том, что оценка тикета неправильно извлекла критерии из тикета.
Кодеру нечего чинить, доработка кода не решит несоответствие
критериев.

**Решение**: вердикт ревьюера теперь несёт причину провала — "проблема
в коде/тестах" (как раньше, уходит кодеру) или "несоответствие
критериев" (уходит обратно в оценку тикета на переизвлечение против
того же текста тикета — не полный рестарт в смысле git/ветки, только
новая генерация критериев). Обе причины одинаково тратят одну из трёх
попыток, различается только адресат.
