# Спецификация цепочки: оценка тикета → кодер → ревьюер → UI-тестировщик

## 1. Оценка тикета (Triage)

**Ответственность**
Читает исходный тикет, решает, достаточно ли в нём данных для реализации.
Если да — извлекает и формулирует критерии приёмки текстом.
Если нет — сам публикует вопрос в тикет и на этом цепочка для этой
задачи завершается. Это не ожидание ответа в реальном времени: агент
не ждёт и не перезапускается — задача просто возьмётся в работу заново
с нуля, когда тикет в следующий раз попадёт в очередь (например, при
изменении его статуса кем-то в тикет-системе).

**Права**
- Только чтение файлов проекта (код ему не нужен на этом шаге)
- Не может редактировать код, не может коммитить
- Публикует вопрос в тикет сам, синхронно, без подтверждения человека —
  сознательное исключение из общего правила approval на внешние
  действия, оправданное тем, что комментарий в тикете обратим и не
  влияет на код или прод

**MCP-доступ**
- Единственный агент в цепочке с доступом к тикет-системе (Jira/аналог)
- Токен — read на чтение тикета + write-scope именно на добавление
  комментария (не на другие операции с тикетом — статусы, назначения
  и т.п. этим токеном недоступны)

**Расшаренные ресурсы**
- Ничего не читает из `.claude/memory/` (у него ещё нет контекста задачи)
- Не пишет в память проекта — критерии передаются дальше через промпт
  спауна следующего агента, не через файл
- Наряду с извлечёнными критериями передаёт дальше и сырой текст
  исходного тикета — как дешёвый пассивный контекст, не для чтения
  каждым агентом, а чтобы ревьюер мог свериться с оригиналом на первой
  итерации (см. раздел 4), если извлечение критериев где-то исказило
  смысл
- Пишет `.work/<id-тикета>/state/ticket-snapshot.md` (сырой текст +
  хэш + дата) в момент извлечения критериев — точка сравнения для
  проверки при резюмировании (раздел 8). Этот же хэш и есть id
  генерации критериев — одноразовые проверки ревьюера (раздел 4)
  привязаны к нему напрямую, отдельного идентификатора не заводится:
  резюмирование в рамках той же генерации их не повторяет, полный
  рестарт с новой генерацией — повторяет

**Модель**: можно использовать быструю/дешёвую — задача классификационная,
не требует глубокого рассуждения.


## 2. Кодер (Coder)

**Ответственность**
Пишет продуктовый код и юнит-тесты по полученным критериям приёмки.
На повторных итерациях — читает фидбек с прошлой попытки (комментарии
ревью или скриншоты расхождений) и правит именно то, что указано.

**Права**
- Работает всегда в выделенной ветке по номеру тикета (например
  `KAZ-112`) — параллельно на ней больше никто не работает, это и
  рабочее пространство задачи, и защита для механической проверки
  тестов в хуке (раздел 3), которая иначе рисковала бы задеть чужие
  незакоммиченные изменения
- Чтение/запись файлов кода
- Запуск линтера, юнит-тестов, `git diff`, `git add`, `git commit`
- Деструктивные операции с БД, `force push`, `sudo` — запрещены
  глобальным хуком безопасности, не переопределяются на уровне агента

**MCP-доступ**
- Нет доступа к тикет-системе — работает только с текстом критериев,
  который ему передали
- При необходимости — read-only доступ к MCP базы данных (посмотреть
  схему), не write

**Расшаренные ресурсы**
- На повторной итерации получает явно, через промпт спауна:
  критерии приёмки (неизменны), комментарии ревью или пути к
  скриншотам с прошлой попытки — это то, чего у него иначе не будет,
  контекст между итерациями не сохраняется автоматически
- Пишет: изменённые файлы + юнит-тесты в репозиторий

**Лимит шагов**: выше, чем у остальных агентов — ему нужно пространство
на итерации внутри своей же задачи.

**Модель**: сильная — здесь основная сложность рассуждения.


## 3. Hook: SubagentStop (после кодера)

Не агент, а системный обработчик события. Проверяет имя только что
завершившегося субагента.

**Что делает**
- Если завершился `coder` — сначала выполняет механическую проверку
  вменяемости тестов прямо в ветке тикета через `git stash`
  (продуктовый код временно откладывается, тесты остаются): прогоняет
  тесты — они обязаны упасть; возвращает код, прогоняет снова —
  обязаны пройти. Ветка эксклюзивна для этой задачи, поэтому `stash`
  безопасен — отдельный git worktree не нужен.
  - Если проверка не применилась чисто (конфликт при откате) — не
    пропадает молча: чекпоинт всё равно создаётся (иначе резюмирование
    после случайного лимита потеряет уже написанный код), но
    помечается флагом "unverified". Сам по себе этот флаг не тратит
    попытку — попытка тратится только при однозначном исходе дальше
    по цепочке (fail от ревьюера), а если ревьюер всё равно скажет
    pass, работа кодера засчитывается без расхода попытки. При
    резюмировании в такой чекпоинт проверка повторяется один раз (ветка
    на этот момент точно эксклюзивна, исходная причина конфликта,
    скорее всего, уже неактуальна); если результат снова неубедителен —
    идём к ревьюеру с тем же флагом, не зацикливаемся на повторах.
  - Если тесты проходят и без кода (тавтологичный тест) — хук сразу
    уходит в счётчик неудач (раздел 8), не тратя цикл ревью. Это
    **тратит** одну из трёх попыток: код уже написан и не годится, это
    реальная работа, которую нужно переделать — в отличие от
    pre-flight отказа по бюджету ниже, где работа даже не начиналась.
- Считает и суммирует токены, потраченные кодером за эту попытку,
  дописывает в `.work/<id-тикета>/state/counter.json` (раздел 8)
- Если проверка пройдена — собирает `git diff` (список изменённых
  файлов, не только текст диффа) и критерии приёмки, фиксирует
  чекпоинт "coder-passed" отдельным коммитом, спаунит ревьюера
- Если завершился кто-то другой — не реагирует (условие внутри хука)

**Доступ**: выполняется в контексте сессии, не имеет собственного
MCP/прав — использует то, что доступно основной сессии (git).

**Надёжность**: хук держится тонким — только маршрутизация и запись
состояния, сложная логика (сама механическая проверка) вынесена в
отдельный, независимо тестируемый скрипт, который хук вызывает. Весь
диспетчер обёрнут в try/catch на верхнем уровне — необработанное
исключение пишет в состояние отметку "хук упал" и уходит по тому же
пути эскалации, что и исчерпанный лимит попыток (раздел 8), не
зависает молча. На каждый шаг — таймаут, зависание тоже считается
сбоем.


## 4. Ревьюер (Reviewer)

**Ответственность**
Оценивает диф на соответствие критериям приёмки и архитектурным
решениям проекта. Получает от хука не текст диффа, а список
изменённых файлов, и читает их целиком в контексте окружающего кода —
диф может быть локально корректным, но ломать вызывающий код за
своими пределами, это не видно по одним изменённым строкам.

Проверяет юнит-тесты по двум критериям сразу: отражает ли тест
реальный исход из критериев приёмки, а не деталь реализации (иначе он
может тавтологично проходить), и есть ли у каждого критерия приёмки
вообще свой тест (трассируемость критерий → тест) — второе ловит
пропущенное покрытие, которое первое не поймает.

На первой итерации в рамках текущей генерации критериев (хэш из
`ticket-snapshot.md`, не номер попытки — резюмирование в рамках той
же генерации эти проверки не повторяет, а новая генерация после
полного рестарта запускает их заново) дополнительно сверяет извлечённые
критерии с сырым текстом исходного тикета (который получил от агента
оценки, не только с готовыми критериями) — ловит случай, где оценка
тикета поняла его неправильно, до того как эта ошибка переживёт все
три попытки незамеченной.

На первой итерации той же генерации, если это фича с UI-проверкой,
дополнительно сверяет черновой сценарий проверки UI-тестировщика с
критериями приёмки, прежде чем он зафиксируется как переиспользуемый
(человек в этом шаге не участвует, роль подтверждения выполняет сам
ревьюер).

**Права**
- Чтение всего репозитория, не только диффа — не может редактировать
  продуктовый код
- Может запускать линтер и статический анализ

**MCP-доступ**
- Нет доступа к тикет-системе
- Нет доступа к БД

**Расшаренные ресурсы**
- Читает `.claude/memory/architecture.md` — сверяет диф с уже
  зафиксированными архитектурными решениями
- Читает `.claude/memory/glossary.md` — для единообразия терминов
- Ничего не пишет в память проекта напрямую — вердикт уходит через
  хук дальше по цепочке

**Формат вывода**: pass/fail, а при fail — ещё и причина провала:
**проблема в коде/тестах** (уходит кодеру, раздел 5) или
**несоответствие критериев** — сверка с тикетом на первой итерации
поймала, что оценка тикета неправильно поняла тикет (уходит обратно в
оценку тикета на переизвлечение, а не кодеру — кодеру там нечего
чинить в коде). Обе причины одинаково тратят одну из трёх попыток —
расход попытки остаётся однородным независимо от того, какая именно
проверка провалилась, различается только адресат.

**Модель**: сильная — нужна глубина рассуждения, не рутинная проверка.


## 5. Hook (после ревьюера)

Проверяет вердикт ревью и причину провала.
- Pass → фиксирует чекпоинт "review-passed" отдельным коммитом,
  спаунит UI-тестировщика, передаёт diff
- Fail, проблема в коде/тестах → передаёт комментарии в счётчик
  неудач (раздел 8), дальше на доработку кодеру
- Fail, несоответствие критериев → возврат в оценку тикета на
  переизвлечение против того же текста тикета (это не полный рестарт
  в смысле git/ветки — с тикетом и веткой ничего не случилось, просто
  нужно поправить извлечённые критерии), новая генерация критериев,
  одноразовые проверки ревьюера для неё запускаются заново. Тоже
  тратит одну из трёх попыток


## 6. UI-тестировщик

**Ответственность**
Прогоняет сценарий визуальной проверки в браузере, делает скриншоты,
сверяет с ожидаемым поведением. Тесты не пишет и не коммитит —
проверка одноразовая.

**Права**
- Браузерная автоматизация (клики, навигация, скриншоты)
- Только чтение кода — не редактирует ничего в репозитории

**MCP-доступ**
- Доступ к браузерному MCP (например, Claude in Chrome)
- Нет доступа к тикет-системе, нет доступа к БД на запись

**Расшаренные ресурсы**
- На первой итерации формулирует черновой `test-scenario.md`, который
  в этом же цикле проверяет ревьюер (см. раздел 4) — сценарий
  фиксируется в `.work/<id-тикета>/state/test-scenario.md` только
  после этого, без участия человека
- На следующих итерациях просто читает уже зафиксированный сценарий
- Пишет скриншоты в `.work/<id-тикета>/screenshots/`, имя файла вида
  `attempt-N_step-M_описание.png`
- На повторной итерации может сравнивать новый скриншот с прошлым
  из той же папки

**Формат вывода**: pass/fail + пути к скриншотам этой попытки.


## 7. Hook (после UI-тестировщика)

- Pass → формирует отчёт, отдаёт в основную сессию
- Fail → передаёт пути к скриншотам в счётчик неудач


## 8. Счётчик неудач

Не агент — состояние, привязанное к конкретной задаче (ключ — id
тикета/ветки, не глобальный счётчик на всю сессию, иначе параллельные
задачи будут мешать друг другу — впрочем, конкурентный запуск одного
и того же тикета исключён на уровне процесса, так что гонки условий
здесь не рассматриваются как риск).

**Расшаренный ресурс**: `.work/<id-тикета>/state/counter.json` — хранит
число попыток, совокупный расход токенов по всем шагам этой попытки
(кодер, проверка тестов, ревьюер, UI-тестировщик) и накопленный
фидбек (комментарии + скриншоты) для передачи кодеру.

Полная сессия каждой попытки (весь диалог кодер → хук → ревьюер →
тестировщик, включая сами промпты — версионирование агентов отдельно
не нужно, факт уже зафиксирован буквально) сохраняется целиком в
`.work/<id-тикета>/state/attempt-N-session.md`. Пишет их сам хук
программно, после каждого шага, а не отдельный агент задним числом.
Если механическая проверка тестов (раздел 3) не смогла применить
откат чисто, это тоже попадает в запись сессии как "проверка
неубедительна: <причина>", а не пропадает молча — ревьюер видит эту
пометку и подстраховывает своим суждением.

**Логика**
- < 3 попыток и в пределах токен-бюджета → возврат кодеру с полным
  накопленным фидбеком
- Бюджет проверяется pre-flight, перед стартом каждого шага, с
  запасом QoS: если остаток бюджета меньше 5% от лимита, шаг не
  стартует вообще, даже если формально ещё есть что тратить —
  тормозим заранее, не впритык к нулю
- `.work/<id-тикета>/state/counter.json` хранит попытки и бюджет как
  два независимых поля, не один счётчик: шаг, не стартовавший из-за
  бюджета, не тратит одну из трёх попыток — это отдельная причина
  остановки, не путается при разборе
- = 3 попытки, ИЛИ сработал QoS-порог по бюджету (что наступит
  раньше) → остановка с сохранением последнего состоявшегося
  чекпоинта (см. ниже)

**Резюмирование при повторном запуске**
- Перед тем как продолжить с чекпоинта, сверяется хэш содержимого
  тикета (или дата апдейта) с `.work/<id-тикета>/state/ticket-snapshot.md`,
  сохранённым агентом оценки в момент извлечения критериев. Если
  тикет менялся — текущее содержимое `state/` и `screenshots/`
  переносится целиком, с зеркальной структурой, в
  `.work/<id-тикета>/stale-<timestamp>/` (не удаляется — принцип
  "человек видит полную историю" сохраняется и через рестарт), работа
  начинается заново с оценки тикета и новой генерации критериев
- Также проверяется, не ушла ли главная ветка вперёд относительно
  точки, от которой была создана ветка `KAZ-112`. Если да — та же
  архивация в `stale-<timestamp>/` и рестарт от актуальной main, без
  попытки разрешить возможный конфликт автоматически
- Если оба условия не сработали — продолжаем со следующего шага после
  последнего зафиксированного чекпоинта, без повторения одноразовых
  проверок текущей генерации критериев (раздел 4). Если последний
  чекпоинт помечен "unverified" — механическая проверка тестов
  повторяется один раз перед тем, как продолжить дальше
- Возврат в основную сессию со статусом "остановлено, нужен человек",
  со ссылкой на `attempt-N-session.md` всех попыток для разбора

**Верхний предел на число рестартов**
Лимит в 3 попытки и QoS-порог по бюджету защищают один цикл. Рестарт
по смене тикета или дрейфу main обнуляет цикл целиком и начинает
новый — без внешнего предела это позволяет обходить лимит попыток
бесконечно, просто часто редактируя тикет. `.work/<id-тикета>/restarts.json`
на уровне корня тикета, не внутри `state/` (переживает каждый рестарт,
который сам же ограничивает), ограничивает: не более 2 полных
рестартов на тикет, то есть максимум 3 цикла по 3 попытки. Исчерпание
— остановка тем же путём, что и обычный лимит попыток, без дальнейших
рестартов.


## 9. Основная сессия

**Ответственность**
Диспетчер всей цепочки — решает, кого вызывать дальше (через хуки
или явно), агрегирует финальный отчёт, при остановке — оповещает
человека с полной историей попыток, а не только последней.

**Расшаренные ресурсы**: видит все MCP-серверы и скиллы проекта по
умолчанию (субагенты видят их же, если не ограничены явно).

# Ревью процесса

**Сильные стороны**
- Минимальные права по умолчанию: тикет-система доступна только
  одному агенту, остальные получают уже извлечённый текст, а не
  прямой доступ — меньше поверхность для ошибок и утечек
- Явное разделение ролей на уровне прав: ревьюер и тестировщик
  физически не могут редактировать код, это гарантия инфраструктуры,
  а не договорённость в промпте
- Числовой предохранитель на цикл кодер-ревью-тест защищает от
  бесконечного зацикливания и неконтролируемого расхода токенов

**Решения, принятые по итогам ревью**

1. Счётчик неудач привязан к id тикета/ветки, не глобальный —
   параллельные задачи не пересекаются.
2. Петля "нужны уточнения" не ждёт ответа синхронно: агент оценки
   публикует вопрос и завершает работу, задача переоценивается заново
   с нуля, когда тикет в следующий раз попадёт в очередь.
3. Публикацию вопроса выполняет сам агент оценки, синхронно, без
   подтверждения человека — токен ограничен write-scope только на
   комментарии.
4. Ревьюер получает список изменённых файлов и читает их в контексте
   окружающего кода, а не только текст диффа.
5. Вменяемость юнит-тестов проверяется механически внутри хука
   (откат кода, тесты обязаны упасть; возврат кода, обязаны пройти) —
   до ревьюера доходит только то, что прошло эту проверку.
6. Полная сессия каждой попытки сохраняется целиком рядом со
   скриншотами — при остановке человек видит весь ход работы, а не
   только последний фидбек.
7. Сценарий UI-проверки на первой итерации сверяет с критериями
   приёмки ревьюер, в том же цикле, что и обычное ревью диффа —
   человек в этом шаге не участвует.
8. `retry-state`/историю сессий пишет сам хук программно, после
   каждого шага — не отдельный агент-суммаризатор задним числом.
   Данные уже структурированы (diff, вердикт, пути к скриншотам),
   пропускать их через ещё один вызов модели — риск потерять то,
   что нужно человеку при разборе.
9. Если механическая проверка тестов не может применить откат чисто —
   это помечается как "неубедительно" и уходит ревьюеру с этим
   флагом, а не пропадает молча и не блокирует цепочку.

**Структура рабочей папки задачи**

Всё, что относится к конкретному тикету, живёт в одном месте, не
размазано по `.claude/memory/`:

```
.work/<id-тикета>/
├── restarts.json              <- переживает рестарты, не архивируется
├── screenshots/
│   └── attempt-N_step-M_описание.png
├── state/
│   ├── ticket-snapshot.md     <- хэш = id генерации критериев
│   ├── counter.json
│   ├── test-scenario.md
│   ├── attempt-1-session.md
│   ├── attempt-2-session.md
│   └── attempt-3-session.md
└── stale-<timestamp>/         <- архив при полном рестарте,
    ├── state/                    зеркалит структуру целиком,
    └── screenshots/               не удаление
```

`.work/` целиком в `.gitignore` — это эфемерная рабочая область
конкретной задачи, а не курируемая память проекта. `.claude/memory/`
(glossary, architecture) остаётся отдельно — то, что должно жить
дольше одного тикета и иметь смысл в отрыве от него. Папку тикета
можно чистить или архивировать после его закрытия.

**`.work/` как канал обмена между субагентами, не только журнал**

У кодера, ревьюера и тестировщика по умолчанию есть read-доступ к
файлам репозитория, включая `.work/`. Это значит, что помимо
передачи данных через промпт спауна (см. описания агентов выше),
любой из них может сам прочитать `.work/<id-тикета>/state/` —
прошлые сессии, зафиксированный сценарий, состояние счётчика — если
ему нужен более широкий контекст, чем то, что явно передал хук.

Два канала не взаимозаменяемы:
- Критичный минимум (критерии приёмки, конкретный фидбек с прошлой
  попытки) — всегда явно в промпте, детерминированно. Агент не
  должен догадываться заглянуть в файл, чтобы узнать, что менять.
- `.work/` — дополнительный слой на случай, если агенту нужна более
  глубокая история, а не замена явной передаче.

**Что осталось открытым**

- Архивирование `.work/<id-тикета>/` после закрытия тикета — чистить
  сразу, или хранить какое-то время на случай повторного открытия.

Полное архитектурное ревью системы в целом (устойчивость хука,
бюджет по токенам, сброс ветки при лимите, трассируемость тестов и
остальное) — отдельным документом: `architecture_review.md`. Все
пункты оттуда закрыты решением, исключением, либо явным "не сейчас"
с обоснованием.
